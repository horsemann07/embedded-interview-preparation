# Lesson 10 — Kconfig, Devicetree, and the Zephyr Build System

> **Learning level:** Beginner → practical  
> **Board for today's experiment:** `qemu_x86`  
> **Our application folder:** `zephyrproject/zephyr/myapp/lesson10_build_system/`  
> **Build folder:** `zephyrproject/build/lesson10_build_system/`  

**Today's goal:** Understand *who decides what goes into the firmware*, *who describes the hardware*, and *who builds the firmware*.

## 1. Imagine building a toy robot

You want to build a robot with a light and a button. You need three different kinds of information:

| Real-world question | Zephyr tool | Example file |
|---|---|---|
| Which *software features* should be enabled? | **Kconfig** | `prj.conf` |
| Which *hardware* exists, and how is it wired? | **Devicetree** | Board `.dts` plus `app.overlay` |
| Which *C source files* should be compiled, and how? | **CMake + Ninja** | `CMakeLists.txt` |
| How do I launch the build/flash/debug commands conveniently? | **west** | Command-line tool |

**Remember it like this:**

- **Kconfig = software switches.** “Enable logging? How big should the stack be?”
- **Devicetree = hardware map.** “Which pin connects to the LED? Which UART is the console?”
- **CMake = build recipe.** “Take `main.c` and combine it with Zephyr.”
- **Ninja = construction worker.** It performs the actual compile/link commands generated by CMake.
- **west = helper/remote control.** It runs build, flash, debug, and workspace/module commands.

One important correction: **Zephyr is not usually a precompiled `.lib` you just attach to a program.** The build system configures and compiles the Zephyr kernel and your application together. You can still store your app completely *outside the Zephyr source folder*; we'll do that in our real-hardware lessons.

## 2. One picture of the whole build

```text
Your source code          Software choices          Hardware description
   src/main.c                prj.conf                 board .dts/.dtsi
       |                         |                            |
       |                    +----v-----+              +-------v-------+
       |                    | Kconfig  |              |  Devicetree   |
       |                    +----+-----+              +-------+-------+
       |                         |                            |
       |                   zephyr/.config              zephyr.dts
       |                    autoconf.h                devicetree_generated.h
       |                         |                            |
       +-------------------------+----------------------------+
                                 |
                      CMakeLists.txt + CMake
                                 |
                        generated Ninja rules
                                 |
                          compiler + linker
                                 |
                      zephyr/zephyr.elf
                      zephyr/zephyr.bin (if produced)
                                 |
                   QEMU run or flash to ESP32
```

This picture is the heart of Lesson 10. The inputs are different, but they come together in **one firmware build**.

### Two phases

1. **Configuration phase:** CMake selects the board and reads Kconfig + Devicetree; Zephyr generates headers and build instructions.
2. **Build phase:** Ninja (normally) compiles the selected C code and links a final firmware image.

Changing `main.c` often requires only recompilation. Changing Kconfig or Devicetree normally requires regeneration of configuration/build data as well. For reliable beginner experiments, use `west build -p always` to get a fresh build.

## 3. Kconfig: the software-switch system

### 3.1 What does `CONFIG_` mean?

You have already seen lines such as:

```ini
CONFIG_PRINTK=y
CONFIG_LOG=y
CONFIG_MAIN_STACK_SIZE=2048
```

These are *requests* to Zephyr's Kconfig system:

- `=y` means “enable” a Boolean option.
- `=n` means “disable” it **when the symbol and its dependencies allow it**. Usually disabled options are simply left out of `prj.conf`.
- A number sets a numeric option, such as a stack size in bytes.
- Some options accept strings or a choice among alternatives.

**Important:** An option might be ignored or rejected because it does not exist, depends on another feature, or conflicts with another option. Kconfig checks those rules; it is not just text substitution.

### 3.2 `prj.conf` is not the final configuration

The build merges configuration settings supplied by the board, SoC, application, and other sources. The final result is typically:

```text
build/lesson10_build_system/zephyr/.config
```

A generated C header, commonly at:

```text
build/lesson10_build_system/zephyr/include/generated/zephyr/autoconf.h
```

makes `CONFIG_*` symbols available to code. **Do not edit generated files directly.** Edit `prj.conf` or the appropriate application/board Kconfig files and rebuild.

### 3.3 Example

```ini
# zephyr/myapp/lesson10_build_system/prj.conf
CONFIG_PRINTK=y
CONFIG_APP_REPEAT_COUNT=4
```

The `APP_REPEAT_COUNT` option will be **defined in our own Kconfig file**, so Zephyr knows it is valid. That's how we create a small application-specific build-time setting.

### 3.4 Reading values in C

```c
printk("Repeat count = %d\n", CONFIG_APP_REPEAT_COUNT);
```

When you change `CONFIG_APP_REPEAT_COUNT=4` to `=2`, the program prints a different value **after rebuilding**, even though `main.c` remains untouched.

### 3.5 Configuration vs runtime

```c
#define LOCAL_BUFFER_SIZE 32    /* C compile-time constant */
```

This is a normal C macro. By contrast, `CONFIG_APP_REPEAT_COUNT` comes from **Zephyr's Kconfig processing**. Neither means a value can be changed while the firmware is running; Kconfig values are build-time choices.

## 4. Devicetree: the board's hardware map

Imagine your ESP32 board:

- It has an ESP32 processor.
- Its OLED is connected to particular pins.
- Its LoRa radio uses SPI and several control pins.
- Its LED connects to a GPIO.

The operating system needs a description of these hardware connections. In Zephyr, this is largely the job of **Devicetree**.

### 4.1 Important file types

| Extension/file | What it means |
|---|---|
| `.dts` | A Devicetree source, often a board's primary description |
| `.dtsi` | A Devicetree source included by another file, often shared SoC data |
| `.overlay` | App-specific edits to the board's Devicetree |
| `.yaml` | A Devicetree binding, telling Zephyr how to interpret node properties |
| `zephyr.dts` | Generated merged Devicetree in the build directory |
| `devicetree_generated.h` | Generated C macros representing the Devicetree |

### 4.2 The idea of a node

Simplified illustration **(not an actual ESP32 board file)**:

```dts
/ {
    aliases {
        led0 = &status_led;
    };

    leds {
        compatible = "gpio-leds";
        status_led: led_0 {
            gpios = <&gpio0 25 GPIO_ACTIVE_HIGH>;
        };
    };
};
```

Read this as:

- There is a hardware-related node called `led_0`.
- `status_led:` gives that node a label that other Devicetree entries can refer to.
- `led0` is a short alias pointing to it.
- `gpios` says what GPIO controller/pin/polarity applies.

**The GPIO number above is only an illustration.** Do not use it as a claimed pinout for your Heltec board.

### 4.3 Alias, chosen, node label — different things

```c
DT_ALIAS(led0)                 /* Node referred to by 'led0' alias */
DT_CHOSEN(zephyr_console)     /* Node selected as console */
DT_NODELABEL(uart0)           /* Node having 'uart0:' label */
DT_PATH(zephyr_user)          /* Node at path /zephyr,user */
```

A node identifier is **not itself** a device pointer. For a real enabled device node you may then use:

```c
const struct device *dev = DEVICE_DT_GET(MY_NODE);
if (!device_is_ready(dev)) {
    /* Device driver is not ready */
}
```

But not every Devicetree node is a device with a Zephyr driver. For example, our experiment will read the root node's **`model` string property**; we do not call `DEVICE_DT_GET()` for the root node.

### 4.4 An overlay changes part of the map

Our QEMU example will use:

```dts
/ {
    model = "Lesson 10: QEMU build-system demo";
};
```

This overrides the top-level board model text for the application. It is a deliberately harmless change that demonstrates how `app.overlay` is merged **without inventing a GPIO or relying on physical hardware**.

Later, on Heltec ESP32 V2, we will use an overlay for practical pin/peripheral configuration such as an OLED or radio (only after checking the exact board definition and drivers).

### 4.5 `status = "okay"` is not sufficient by itself

Making a Devicetree node available typically also requires that a suitable driver is built, the necessary Kconfig options/dependencies are satisfied, and hardware/pinmux settings are correct. **Devicetree describes hardware; Kconfig selects software support.** They work together.

## 5. CMake, Ninja, and west

### 5.1 `CMakeLists.txt`

This is the minimal application build recipe:

```cmake
cmake_minimum_required(VERSION 3.28.0)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(lesson10_build_system)

target_sources(app PRIVATE src/main.c)
```

Read it line by line:

1. Require an appropriate CMake version.
2. Ask CMake to locate the Zephyr build system and load its settings.
3. Give this app a project name.
4. Tell Zephyr's `app` target to compile `src/main.c`.

Note that the Zephyr build system creates the `app` target; our source gets added to it. The final firmware includes the selected Zephyr kernel/driver code plus the application.

> If your installed Zephyr checkout requires a different CMake minimum, follow that checkout's requirements. `3.28.0` is used in the current Zephyr documentation.

### 5.2 Why `west`?

`west` is a front-end. It can call the underlying tools for you:

```powershell
west build ...       # Configure + compile
west build -t run ...# Start supported emulation targets
west flash ...       # Flash supported physical boards
west debug ...       # Start a supported debug workflow
west update          # Update repositories/modules in the west manifest
```

**Not all boards support every target.** QEMU `run` is for the emulator; `west flash` is relevant later for your ESP32.

### 5.3 Board target vs application folder

```powershell
west build -b qemu_x86 .\myapp\lesson10_build_system
```

- `qemu_x86` chooses the **target board**.
- `.\myapp\lesson10_build_system` chooses the **application**.

These are independent dimensions. In principle, the same application can target another board when all required APIs/peripherals are available and its configuration is suitable.

## 6. Kconfig vs Devicetree vs CMake: quick test

| Requirement | Where does it belong? | Why? |
|---|---|---|
| Enable logging | `prj.conf` / Kconfig | Software feature |
| Set main thread stack size | `prj.conf` / Kconfig | Kernel/software configuration |
| Choose GPIO pin for an LED | Devicetree | Hardware wiring |
| Select a UART as console | Devicetree `/chosen` (and relevant Kconfig settings) | Hardware instance + console support |
| Add `src/display.c` to build | `CMakeLists.txt` | Compile this source file |
| Pick `qemu_x86` board | `west build -b ...` | Build target |
| Print text every 500 ms | `main.c` | Application behavior |
| Set an app's build-time loop count | App `Kconfig` + `prj.conf` | Configurable software behavior |

**Memory trick:** Kconfig = *what software?* Devicetree = *what hardware?* CMake = *what source gets built?*

## 9. Hands-on experiment: full working application

We'll use **five files**. This is slightly more than our usual three because we want to see **all three configuration systems** in action.

### File 1 — `CMakeLists.txt`

Create `zephyr/myapp/lesson10_build_system/CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.28.0)

find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})
project(lesson10_build_system)

target_sources(app PRIVATE src/main.c)
```

### File 2 — `Kconfig`

Create `zephyr/myapp/lesson10_build_system/Kconfig`:

```kconfig
# SPDX-License-Identifier: Apache-2.0

mainmenu "Lesson 10 build configuration"

config APP_REPEAT_COUNT
    int "How many greetings should we print?"
    range 1 10
    default 3
    help
      Controls the number of greetings printed by Lesson 10.
      This demonstrates a custom application Kconfig option.

source "Kconfig.zephyr"
```

**Explanation:**

- `config APP_REPEAT_COUNT` creates the symbol `CONFIG_APP_REPEAT_COUNT` used in code and `prj.conf`.
- `int` means an integer.
- `range 1 10` limits allowed values.
- `default 3` applies unless a valid override is supplied.
- `source "Kconfig.zephyr"` also loads Zephyr's normal Kconfig options. Without this, our application Kconfig would hide important standard kernel configuration choices.

### File 3 — `prj.conf`

Create `zephyr/myapp/lesson10_build_system/prj.conf`:

```ini
CONFIG_PRINTK=y
CONFIG_APP_REPEAT_COUNT=4
```

### File 4 — `app.overlay`

Create `zephyr/myapp/lesson10_build_system/app.overlay`:

```dts
/ {
    model = "Lesson 10: QEMU build-system demo";
};
```

An application-level `app.overlay` is normally auto-discovered by Zephyr's build system when it is in the application directory. The result becomes part of the merged Devicetree.

### File 5 — `src/main.c`

Create `zephyr/myapp/lesson10_build_system/src/main.c`:

```c
/*
 * Lesson 10: Kconfig + Devicetree + Build System
 *
 * Works with our QEMU experiment.
 */

#include <zephyr/kernel.h>
#include <zephyr/devicetree.h>
#include <zephyr/sys/printk.h>

/* DT_ROOT is the root node ( / ). Its "model" text is in app.overlay. */
#define BOARD_MODEL DT_PROP(DT_ROOT, model)

int main(void)
{
    printk("\n=== Lesson 10: Build System ===\n");
    printk("Board model (Devicetree): %s\n", BOARD_MODEL);
    printk("Greeting count (Kconfig): %d\n", CONFIG_APP_REPEAT_COUNT);

    for (int i = 1; i <= CONFIG_APP_REPEAT_COUNT; i++) {
        printk("Hello from Zephyr! %d/%d\n",
               i, CONFIG_APP_REPEAT_COUNT);
        k_msleep(500);
    }

    printk("Lesson 10 demo finished.\n");
    return 0;
}
```

**Walk through the code:**

- `BOARD_MODEL` takes a string from **Devicetree**.
- `CONFIG_APP_REPEAT_COUNT` takes an integer from **Kconfig**.
- `target_sources()` in **CMake** causes this `main.c` to be compiled.
- `k_msleep(500)` pauses the main thread for half a second; other kernel work can continue.

> QEMU may remain running even after `main()` returns. This is expected; use the QEMU exit shortcut shown by your emulator or terminate the QEMU process when done.

## 15. Compare Zephyr, FreeRTOS, and ThreadX

| Question | Zephyr | FreeRTOS | ThreadX (Eclipse ThreadX) |
|---|---|---|---|
| Typical software configuration | Kconfig (`prj.conf`, `CONFIG_*`) | `FreeRTOSConfig.h` plus project/build settings | `tx_user.h` / compile-time defines plus integration settings |
| Hardware description | Devicetree and board definitions | Commonly vendor HAL, BSP, pin definitions; not one universal Devicetree system | Commonly board support package, HAL, integration code |
| Build integration | Zephyr CMake + west; Ninja/Make underneath | Application/vendor build system, CMake or IDE | Application/vendor build system, CMake or IDE |
| Compile application and kernel together? | Usually yes, configured as one firmware | Commonly yes | Commonly yes |
| Source can live outside the RTOS checkout? | Yes, normal and supported | Yes | Yes |
| Typical physical board flashing | `west flash` when board supports it | Vendor tools, IDEs or custom scripts | Vendor tools, IDEs or custom scripts |

**Do not confuse:** Zephyr Devicetree is not the same as device discovery during runtime. On most microcontrollers, Devicetree information is processed **at build time**.

## 17. Common mistakes and fixes

| Problem | Likely cause | What to do |
|---|---|---|
| Output from the previous lesson | Reused an old build directory/source cache | Run the exact `west build -p always ... -d ...` command |
| `CONFIG_APP_REPEAT_COUNT` not recognized | Missing/misnamed `Kconfig`; typo in option name | Create `Kconfig` at app root, check `source "Kconfig.zephyr"`, rebuild |
| Greeting count didn't change | Changed file but used a stale build | Confirm `prj.conf` path, use `-p always`, inspect `.config` |
| Devicetree model didn't change | Overlay not discovered or build not regenerated | Confirm `app.overlay` location, rebuild pristine, inspect `zephyr.dts` |
| CMake fails before compile | Toolchain, CMake version, or incorrect working folder | Activate `.venv`; inspect exact error; verify Zephyr SDK install |
| `west build -t run` fails | QEMU environment/runtime issue | Confirm QEMU installation and repeat earlier working Hello World setup |
| `menuconfig` doesn't open | Terminal/Windows curses dependency | Skip interactive UI and edit `prj.conf` |
| `DEVICE_DT_GET()` unresolved | Node lacks a usable enabled driver instance | Confirm node status, binding, Kconfig, driver, and `device_is_ready()` |
| Wrong board selected | Build dir cached another `-b` | Use a new build dir and `-p always` |

### Helpful general debugging commands

```powershell
# From the Zephyr source folder
west --version
west boards | Select-String "qemu_x86"
Get-ChildItem ..\build\lesson10_build_system\zephyr
```

When something fails, paste the **first actual error line and about 15–20 lines around it**. We can fix the precise problem instead of guessing.

```text
devicetree_generated.h = generated C representations

CMakeLists.txt = list application sources and connect to Zephyr
Ninja = performs compiled build work
west = convenient commands to build/run/flash

BUILD OUTPUT (do not edit):
  build/.../zephyr/.config
  build/.../zephyr/zephyr.dts
  build/.../zephyr/include/generated/zephyr/autoconf.h
  build/.../zephyr/include/generated/zephyr/devicetree_generated.h
  build/.../zephyr/zephyr.elf
```

### A final analogy

Imagine making a sandwich:

- **Kconfig:** Which ingredients do you want enabled—cheese, tomato, sauce?
- **Devicetree:** Which ingredients and kitchen equipment actually exist and where are they?
- **CMake:** The recipe that lists what to combine.
- **Ninja:** The cook executing the recipe.
- **west:** The person who tells the kitchen, “Start cooking!”

With Zephyr, these ideas make firmware builds understandable, reproducible, and portable between boards.
